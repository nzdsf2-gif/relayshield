## 1. WHERE THINGS ACTUALLY STAND, read fresh rather than assumed

    expo               ~51.0.0
    react-native       0.74.5
    react              18.2.0
    @solana-mobile/mobile-wallet-adapter-protocol(-web3js)   ^2.1.3
    @solana/web3.js    ^1.91.7

**The native `android/` folder is checked in, AND the project uses Expo's config-plugin system**
(`withRemoveDebugPermissions.js`, built on `@expo/config-plugins`). That combination matters: it
means the native folder is meant to be regenerated by `expo prebuild`, not hand-maintained forever,
which is the supported upgrade path rather than a from-scratch native migration. It also means
`expo prebuild --clean` will **wipe and regenerate** `android/`, so anything hand-edited directly in
that folder rather than through a config plugin will be lost and must be re-applied or converted
into a plugin first.

**Two Solana-specific things are load-bearing and must be checked, not assumed, before this ships:**

- `src/utils/mwa.ts` is the ONLY file touching Mobile Wallet Adapter. MWA is not Seeker-exclusive —
  it works on any Android phone with a compatible wallet app (Phantom, Solflare) installed, connecting
  via Android intent — so **it does not need to be removed or gated for the Google Play build.** It
  needs re-testing after the SDK bump, same as everything else that touches native code, but it is
  not a reason to fork the codebase by platform.
- **Three files hardcode a Solana dApp Store update/review path with no Google Play equivalent**:
  `UpdateNudge.tsx` (in-app version-check banner deep-links to the dApp Store listing),
  `FeedbackPrompt.tsx` (deep-links to `solanadappstore://details?id=...` for a review ask), and
  `SettingsScreen.tsx` (the publisher-side dApp Store link). All three need a platform branch
  (`Platform.OS` plus a store-detection or a build-time flag) pointing at the Play Store listing
  instead, or a Solana-only user gets an Android nudge that goes nowhere.

## 2. THE THREE WORKSTREAMS, AND WHY THEY GO IN ONE BUILD RATHER THAN THREE

Andrew asked for the Expo upgrade to carry the SIM-swap fix and the attack-chain graphic in the
same pass, and that is the right call rather than a convenience: **all three require a new native
build and a new store submission regardless of order**, so splitting them into separate releases
multiplies the review-cycle cost (Google Play: 3–7 days each) for no isolation benefit — none of the
three touches the other two's code paths, so there is no meaningful risk of them interfering, only
of paying the review tax three times instead of once.

### 2a. Expo SDK 52 or 53 — the Google Play gate itself

**Recommendation: target SDK 53, not 52.** 52 is the minimum that satisfies the 16KB native-library
alignment requirement (React Native 0.77+, which 52 ships), but 53 is the current stable SDK as of
this writing and skipping straight to it avoids paying the upgrade-pain cost twice in quick
succession. If 53 turns out to have its own blocking issue once actually attempted, 52 is the fallback,
not the target.

**What actually needs verifying, each one a real regression risk on THIS app specifically:**

- **`expo prebuild --clean` regenerates `android/` from `app.json` + config plugins.** Confirm
  `withRemoveDebugPermissions.js` survives the regen correctly (it should, since it's a proper
  plugin) — but also confirm nothing was hand-edited directly in `android/app/src/main/AndroidManifest.xml`
  outside that plugin's reach. If anything was, it needs to become a plugin BEFORE the prebuild, or
  it silently disappears.
- **The release signing keystore.** This app has a documented history here: the original release
  key is unrecoverable, and a rebuild once silently signed with the wrong keystore
  (`eas build --local` vs `./gradlew assembleRelease` directly). Confirm the SDK-53 build signs with
  `cryptoshield-release.keystore` and verify with `apksigner verify --print-certs` before any upload
  — this is the single most expensive mistake this app has already made once.
- **`assetlinks.json` / Digital Asset Links**, which is what makes Phantom/Solflare trust the app's
  MWA identity rather than showing "identity could not be verified." Confirm the SHA-256 fingerprint
  served from the landing-page Worker still matches the SDK-53 build's signing cert.
- **SYSTEM_ALERT_WINDOW must still be absent** post-rebuild — verify via `apksigner`/manifest dump,
  same check this project already runs after every release.
- **The three Solana-dApp-Store-only deep links (section 1)** need their Google Play branch added
  in this same pass, or Android users get dead nudges.

**Effort: 2–4 days**, weighted toward verification rather than code — the actual `expo install expo@53`
+ dependency bump + `expo prebuild --clean` is typically under a day; the remaining time is
confirming every item above didn't silently regress, which is exactly the kind of check this repo's
own CLAUDE.md insists on running rather than assuming.

### 2b. SIM-swap enrollment — already scoped, ~3 days, unchanged by this decision

Full detail in `simswap_crypto_shield_mobile_scope.md`, still accurate as of this session
(`checkSimSwap()` confirmed to still have zero callers). Nothing about the Android decision changes
that scope; it rides in the same build because a build is happening anyway.

### 2c. The attack-chain graphic — built on infrastructure that already exists

`relayshield_breach_monitor.py`'s `ATTACK_CHAINS` correlation model and `/v1/metered/incident-timeline`
(built 2026-09-23) already return a real `chain_matched` verdict for an identity's breach, SIM-swap
and domain-phishing signals. The graphic should call that endpoint and render the user's OWN actual
chain (or the honest "nothing found" state), not a static illustration — this is the same reasoning
already applied elsewhere in this repo: two implementations of one correlation model is the
single most-repeated defect in the codebase, and a generic diagram would be exactly that, one layer
removed.

**This item depends on 2b being live first**: SIM-swap is one of only two signal types
`incident-timeline` can ever match a chain against (breach and domain-phishing being the other), so
building the graphic before enrollment exists means it can only ever show the domain-phishing chain,
never the SIM-swap one — half the point of asking for it. Sequence: 2b, then 2c.

**Scope, roughly a day**: a screen reading the endpoint's response (email required, phone optional
once 2b ships) and rendering a simple linear chain view — breach → SIM-swap/domain-phishing →
wallet exposure — with the "nothing found" state given equal visual weight, per this repo's own rule
that "we could not check" and "it is fine" must never look the same, and a clean result is the most
common honest outcome, not a case to bury.

## 4. BRAINSTORM: IMPROVING THE ODDS ON GOOGLE PLAY, NOT JUST SHIPPING TO IT

Asked for explicitly. These are ranked by leverage, not effort, and marked as mine to be overruled.

**1. Cross-promote from the installed base this repo actually has, before spending a dollar on Play
ads.** The Telegram bot and WhatsApp webhook have real, measured traffic (`/v1/wallet-risk` and
`/v1/link-check` keyless calls, the Mini App's catalogue listings). Crypto Shield Mobile has none of
that distribution today — `/wallets`, `/addwallet` and the crypto-tier Telegram commands exist, but
nothing in the bot points a crypto-curious user at the standalone app. **Add one line to the crypto
command tier's `/help` output and to `handle_checkvault`/`handle_checktoken`'s replies**: "Want this
running continuously in the background? Crypto Shield Mobile does this automatically." This is
free, it's the highest-intent audience available (people already asking the bot to check a wallet),
and it's a few hours of work, not a scope item.

**2. Fix the review-count problem before launch, not after.** TODO.md's own item 66 found exactly
one confirmed real Solana subscriber and two five-star reviews on the whole listing. A Play Store
listing with zero or near-zero reviews at launch converts far worse than one with even five honest
ones — this is well-documented app-store behavior, not a guess. The in-app nudge item 66 already
flagged as "still on deck" (asking a happy subscriber for a rating, surfaced in-app rather than only
by email) should ship in THIS build, timed to fire after a clean scan result — the single best
moment, per this repo's own doctrine on when to ask.

**3. Lead with the thing competitors don't have, in the FIRST screenshot.** Blowfish and Pocket
Universe (the named competitors in TODO.md) are both on-chain-only: they catch a bad transaction at
signing time. Crypto Shield's actual differentiator — SIM-swap and breach monitoring, i.e. catching
the attack BEFORE it ever reaches a signature prompt — is currently buried in the "What it does"
bullet list rather than the headline. The store listing's tagline ("The only wallet security app
that watches your credentials, not just your chain") already says this correctly; the screenshots
and the first 10 seconds of the description should lead with it too, since that's what a Play Store
browser actually reads before a wall of bullets.

**4. Price parity is still unresolved and will look sloppy if launched inconsistent.** TODO item 7
already flagged $11.99/mo for Play Billing's 15% rate vs. $10.99 on Solana, and that this needs
per-platform price branching in `PaywallScreen.tsx` (currently one hardcoded Stripe link). Decide
and implement this in the SAME build as the SDK upgrade — a paywall that still says $10.99 while
Play Billing charges $11.99 is a trust problem on day one, and the trial-framing copy from item 67
needs the same per-platform treatment.

**5. Do not repeat the Solana cert mistake as a Play Store mistake.** Google Play does NOT require
unpublish-and-republish on a cert change the way the Solana dApp Store did — Play tracks app
identity by package name + upload key, and a lost upload key has its own (painful but non-destructive)
recovery process via Play Console support, not a forced app-record replacement. Still: back up the
Play upload keystore the same way the Solana release keystore was backed up (Proton, checksum-verified)
the FIRST time it's generated, not after a scare.

**The condition that would make me reconsider any of the above**: if the crypto-command
cross-promotion in item 1 produces measurable clickthrough (attributable via a `?source=` style
key on whatever link the bot sends) before the Play submission ships, that is real evidence about
demand and should reweight how much marketing effort goes into the listing itself versus the
distribution channel that's already working.
