## Item 1 — the MCP server. What is proven, and what is not.

The honest split matters here, because "it is fixed" and "the half I can see is fixed" are
different claims and only one of them is mine to make.

**PROVEN, by running it rather than reading it.** `relayshield_mcp_server.py` at the repo root
starts, completes a real MCP `initialize` handshake, and hands over all 8 tools:

    check_breach, check_sim_swap, check_domain_lookalikes, check_oauth_watchlist,
    check_infostealer, scan_url, scan_file, check_scan_result

So the file the configs were repointed AT is sound. Whatever else is true, the destination of the
fix is not the problem.

**NOT PROVEN, and it cannot be from here.** Whether your Mac's Claude Desktop and Claude Code
configs now name that file, and whether the interpreter they name can import it. Those configs live
in `~/Library/Application Support` and `~/.claude.json` — directories this container has never seen.
That is the same blind spot that made the original outage invisible, so I am not going to guess past
it.

### A SECOND CAUSE WITH THE SAME SYMPTOM, found by running the server against two SDKs

This is the part worth reading even if the server is already back up.

`relayshield_mcp_server.py` registers its tools with the pre-2.x `mcp` decorator API. The `mcp` SDK
removed that in 2.x. Measured both ways today:

- `mcp` **1.29.1** — handshake completes, 8 tools. Fine.
- `mcp` **2.1.1** — dies at **import** with `AttributeError: 'Server' object has no attribute 'list_tools'`.

A client launches this file by absolute path using whatever interpreter its config names. So an
unrelated `pip install -U mcp` into your anaconda python kills the server with **no config change
and no commit in this repo** — and the client reports "disconnected", which is character-for-character
what the path bug looked like on 2026-09-05.

Two different causes, one symptom, and the config looks correct in both. That is the same shape as
"a 402 is not proof the right Lambda answered": when two causes produce the same success or failure
shape, you have to check the field that differs between them.

### So the check is now a verdict, not a log tail

Item 1 as written said "run `mcp_inventory.sh` and read section 3; a clean run shows no new ENOENT
lines after the restart timestamp." That is a human eyeball over 25 log lines — and eyeballing that
log is precisely what nobody did while it repeated the answer every few minutes for hours.

`tools/mcp_selftest.py` (new, committed) does the client's own job instead. It spawns each
configured server with the interpreter and env that config names, completes `initialize`, calls
`tools/list`, and prints **ACTIVE** or **DEAD**. Exit status is 0 only if every server answered.

It stops at the handshake and never calls a tool, because a tool call costs money — the same
boundary `mpp_settlement_selftest.py --reads-only` draws, for the same reason.

It separates the three failures that all present as "disconnected", and names the fix for each:

| What the log shows | What it means | Fix it names |
|---|---|---|
| ENOENT on the script | the clone moved | `fix_mcp_config_paths.py --write` |
| `ModuleNotFoundError` | wrong interpreter | install into *that* python |
| `AttributeError` on `list_tools` | `mcp` went to 2.x | pin `mcp<2` for that interpreter |

Verified against all three cases before committing: a good interpreter reports ACTIVE with 8 tools,
`mcp` 2.1.1 reports DEAD naming the pin, and a script at a path that no longer exists reports DEAD
naming `fix_mcp_config_paths.py`. Env values are redacted to a prefix and a length, per rule 12,
because this output goes into a chat.
